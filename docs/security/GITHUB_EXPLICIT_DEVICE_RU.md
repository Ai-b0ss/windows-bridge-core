# Обязательный адресат GitHub-команд (A3)

Исправление устраняет приём одной задачи несколькими устройствами при отсутствии `target_device`. Прежняя проверка отклоняла несовпадение только для истинного значения поля; отсутствие, `null`, пустая строка, `false` и `0` проходили её. Новый контракт закрывает этот путь до сохранения pending-запроса, захвата задачи журналом и вызова RPC.

## Контракт и совместимость

| Вход или отправитель | Поведение |
| --- | --- |
| Комментарий `ff-win-github-comment-v5` от разрешённого отправителя | Единственная принимаемая схема задачи; обязателен строковый `target_device` верхнего уровня |
| Старые версии, отсутствующая схема, result/health/fast-result envelopes | Не являются исполняемыми задачами |
| Любая операция: чтение, запись, `computer_use`, `durable_call`, неизвестное имя | Одинаковое требование адресата; списки безопасных операций не дают исключения |
| `execution_context`: auto, interactive, background | Не меняет адресата и не обходит проверку |
| `tools/bridge_remote_gh.py` | `--list` читает метаданные inbox; исполнение требует точного `--device` из списка. Вспомогательный `submit` также проверяет имя до API-вызова |
| `ff_win_github_client.py` | Берёт адресат только из `config.device`; проверяет до получения токена. Вспомогательный `submit` проверяет поле до чтения redirect и POST |
| `ff_win_github_smoke_test.ps1` | Всегда передаёт `config.device`; отклоняет некорректное значение до поиска GitHub CLI и получения токена |
| Подключённый GitHub MCP или вручную сформированный комментарий | Должен явно передавать то же поле; проверка daemon действует независимо от клиента |

Адресат сравнивается с локальным `DEVICE` без учёта регистра, как и прежде. Никаких преобразований чисел в строки, обрезания пробелов, wildcard, псевдонимов, подстановки имени отправителя, адресата из `args`, имени issue или redirect нет. Пустые значения, пробелы по краям и управляющие символы запрещены. Обычные имена установленных устройств и явно заданные пользовательские имена сохраняют прежнее сравнение. Формат имён в `bridge_remote_gh.py` остаётся прежним: 1–100 символов ASCII из букв, цифр, `.`, `_`, `:`, `-`.

Повторяющиеся ключи JSON, включая экранированное написание `target_device`, отклоняются во всём конверте и вложенных объектах. Генераторы на `json.dumps` и `ConvertTo-Json` их не создают. Разрешения владельца, ограничения Windows и классификация безопасных операций этим изменением не расширяются.

## Пути исполнения и диагностика

Первичное сканирование inbox, обычный poll, сканирование архивных поколений и восстановление файлов `pending-requests` сходятся в `submit` → `parse_task`. Worker `process` повторно проверяет исходный комментарий и соответствие переданного task; исполняет заново разобранный конверт. Поэтому прямой вызов worker или ранее поставленная в очередь задача без адресата не обходят проверку.

Единственный найденный вызов общего `ff_win_transport_core.execute_task` из GitHub transport находится в этом worker. Общий модуль выполняет локальный RPC и ведёт журнал; сам по себе он не принимает комментарии GitHub. Локальный `/rpc`, background-agent и direct-клиент используют другой вход и не меняются в A3. Они не являются альтернативными обработчиками GitHub-комментариев.

Для задач с корректной схемой и остальными обязательными полями отказ адресата записывается существующим ограниченным локальным `trace` как `task_rejected`: `TARGET_DEVICE_REQUIRED` либо `TARGET_DEVICE_MISMATCH`; несовпадение отдельного task и комментария — `TASK_VALIDATION_MISMATCH`. Запись содержит ID комментария и код причины, без аргументов, токенов и присланного адресата. Trace остаётся диагностикой с прежними настройками отключения и ротации, а не новым удалённым ответом. Посторонний daemon не заменяет комментарий своим отказом и не мешает целевому устройству получить задачу.

Для корректно адресованных задач уже подготовленные результаты в outbox публикуются прежним путём без повторного исполнения. Legacy outbox без адресата сохраняется для сверки, но сам по себе не даёт разрешения обойти валидацию при восстановлении. Журнал мутаций, ключ `client_id::task_id`, конфликт содержимого и правила неизвестного исхода не меняются.

## Миграция старых pending-задач

1. Обновить отправителей: выбрать конкретное устройство через чтение метаданных inbox / `--list`; заполнить его точное имя в `target_device` или `config.device`. Не угадывать адресат по компьютеру, на котором запущен клиент.
2. Сохранить исходные комментарии, `pending-requests`, outbox и журналы. Исправление ничего из этого не удаляет и не приписывает старым задачам адресата автоматически. Корректные задачи с адресатом восстанавливаются прежним путём.
3. Для старой задачи без адресата проверить результаты, outbox, журнал и фактический эффект на всех устройствах, которые раньше могли её принять. Отсутствие ответа или новый отказ валидации не доказывает, что старая версия ничего не исполнила.
4. Только после выяснения исхода исправить исходный комментарий владельца, добавив точный адресат, либо отправить явно адресованный конверт. Сохранить прежние `client_id`, `task_id`, `op` и `args`, чтобы существующий журнал мог вернуть результат или запретить повтор. Не создавать новый ID ради обхода `TASK_OUTCOME_UNKNOWN`, конфликта или истёкшего результата. Адресат не входит в прежний digest журнала; это намеренно сохраняет защиту от повтора при миграции на том же устройстве.
5. Если исход неизвестен, сначала независимо проверить эффект и согласовать дальнейшее действие. Повтор на другом устройстве имеет отдельный журнал и не обеспечивает межмашинную дедупликацию.

Старый неадресованный pending-файл остаётся на месте и не исполняется при рестарте. Если исправлен исходный комментарий, его следующая загрузка может пройти проверку; сохранённый старый файл сам по себе по-прежнему не даёт разрешения на исполнение. После успешной публикации используется прежняя очистка pending.

## Изолированная проверка

`tests/test_github_explicit_device.py` воспроизводит отказ до исправления и проверяет матрицу адресатов, два устройства и два агента, чтение и мутации, алиасы, вложенный адресат, дубликаты JSON, повторную проверку worker, startup/archive/recovery, сохранность legacy pending, ранний отказ обоих Python-клиентов и PowerShell smoke. Проверяется работа настоящего HTTP RPC-клиента с локальным сервером-заглушкой и отдельными SQLite-журналами устройств: корректная мутация доходит один раз, дубликат возвращает кэш, смена содержимого вызывает конфликт.

Команды проверки: `python -m unittest discover -s tests -p test_github_explicit_device.py -v`, полный `python -m unittest discover -s tests -v`, `python tests/integration/isolated_rpc_smoke.py`, `git diff --check`. Manifest обновляется после staging по SHA-256 байтов `git show :path`, затем проверяется `tests/test_manifest_matches_git.py`.

Это локальная проверка исходников и изолированного RPC. Она не доказывает доставку через настоящий GitHub inbox, установку исправления или поведение рабочего Bridge.
