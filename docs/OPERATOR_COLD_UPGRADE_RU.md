# Безопасная подготовка холодного обновления Windows Bridge

Инструмент: `tools/cua_cold_rollback_bundle.py`. Он выполняет проверку
происхождения установленного ядра, сохраняет ограниченный набор управляемых
файлов и проверяет или восстанавливает снимок. **Не останавливает Bridge,
не перезапускает службы и не запускает обновление самостоятельно.**

## Почему требуется отдельная процедура

На этой машине `%LOCALAPPDATA%\FF-Windows-Bridge` — junction к
`K:\FF-Windows-Bridge`. Для действий с файлами использовать физический
путь `K:\FF-Windows-Bridge\bridge-v3`, не переходить через junction.
Действующий код соответствует Git-коммиту `a73aee9` (109 файлов), но
установленный манифест относится к `cdd9541` (104 файла). Перед
развёртыванием старый манифест нужно независимо доказать по Git-объектам.

Внутри `.cua-deploy` остались четыре журнала старых транзакций, все
311 исходных резервных файлов и четыре манифеста подтверждены SHA-256.
**Нельзя их удалять или автоматически восстанавливать без расследования**;
снимок оставляет их без изменений.

## Подготовка и резервирование

1. Выбрать фиксированный Git-коммит кандидата и подтвердить чистоту
   рабочего дерева, успешные локальные тесты и GitHub CI.
2. Запустить read-only preflight, указав полный SHA доверенного коммита:
   `python tools/cua_cold_rollback_bundle.py preflight --repo <checkout> --runtime K:\FF-Windows-Bridge\bridge-v3 --trusted-head <40-hex-sha>`.
3. Сохранить снимок **с новым непустым именем** в
   `K:\FF-Windows-Bridge\recovery\<уникальный-набор>`, вне runtime:
   `python tools/cua_cold_rollback_bundle.py capture --repo <checkout> --runtime <physical-runtime> --snapshot <new-path> --trusted-head <40-hex-sha>`.
   Каждая исходная копия сверяется по SHA-256; запись выполнена отдельно
   от работающего Bridge, а пользовательский state (в том числе журналы,
   браузерные профили и записи процессов) не перемещается.
4. Независимо проверить `verify --snapshot <path>`. Проверка должна
   отвергать отсутствующий файл, подменённый манифест, расхождение хеша,
   изменённое или недоказанное происхождение.

## Развёртывание: обязательные условия

Снимок **не является разрешением на остановку агента**. Сейчас существуют
отдельные хранители и более одного экземпляра Bridge, а основной агент
учитывает множество ранее созданных сессий. Перед холодным
обновлением нужно отдельно подтвердить завершение работ и точные PID
с токенами создания процессов. Не использовать общий taskkill для всех
агентов, не трогать FlClash, браузер, интерактивные задачи или чужие
экземпляры. Прежний агент не поддерживает безопасную передачу сокета
новой версии, поэтому замена требует согласованного короткого простоя.

Автоматическое восстановление после неудачного запуска должно выполнять
внешний супервизор, не загруженный из заменяемого каталога. Нельзя
считать установленный код пригодным только из-за успешной записи файлов:
требуются health, ping через внешний маршрут, исходная авторизация,
сохранность owner stop и keeper, а также проверка загруженного SHA агента.

## Два экземпляра из одного runtime: 39073 и 39076

При восстановлении целевого порта 39073 допускается не останавливать
живой prelogin-сервер `ff_win_v3_main.py serve --host 127.0.0.1
--port 39076`, в том числе запущенный через junction, если Win32_Process
однозначно подтверждает его командную строку и PID. Неизвестный порт,
второй флаг `--port`, `--also-listen`, `--standby`, другой хост,
любой работающий 39073 или `ff_win_v3_keeper.ps1` запрещают запись.

В режиме сохранения 39076 требуется явный контекст в разрешённом плане
сторожа: `port=39073`, `peer_port=39076`. При ручном offline-откате
добавить `--target-port 39073 --peer-port 39076`. Без них сохраняется
строгий запрет на запись при любом активном экземпляре.

Пока 39076 работает, разрешается атомарно заменять лишь изменённые
`.py` и манифест. Неизменённые файлы не переписываются. Если новый
релиз требует модификации других файлов, откат блокируется до безопасной
остановки экземпляров. Это исключение не разрешает запуск нового
деплоймента или остановку процессов: оно касается только проверенного
аварийного восстановления.

## Восстановление

Только после **проверенного завершения всех процессов агента и keeper,
читающих заменяемый runtime**:
`python tools/cua_cold_rollback_bundle.py restore --runtime <physical-runtime> --snapshot <verified-bundle> --offline-confirmed`.

Команда сама проверяет процессы Windows и отказывает при найденном
агенте или keeper. Она восстанавливает только известные Git-файлы и
старый манифест, удаляя новый файл кандидата лишь при совпадении его
хеша с Git. При чужих правках — отказ до первого изменения. Не
восстанавливаются PID, личные процессы, state, внешние файлы и журналы
транзакций. После восстановления следует отдельно запустить штатный
keeper и проверить внешнюю связь. До выполнения и проверки такой
процедуры на реальной машине автоматическое обновление запрещено.

## Независимый предохранитель для запуска новой версии

Сначала создать автономный комплект командой
python tools/cua_cold_rollback_bundle.py kit --repo <checkout> --kit-root <new-recovery-dir>
и независимо проверить:
python tools/cua_cold_rollback_bundle.py verify-kit --kit-root <new-recovery-dir>.
Операция копирует по Git-хешам семь зафиксированных файлов и выполняет
изолированную проверку импортов, не обращаясь к работающему ядру.

Сторожевой процесс: tools/cua_cold_recovery_watchdog.py. Перед любым
прерыванием связи он должен быть скопирован в независимый каталог рядом
с резервной копией вместе с проверенными зависимостями, и запущен
отдельным процессом Windows Task Scheduler, не через активный Bridge.

Сторож принимает только явно разрешённый локальный план
с полями: schema=ff-bridge-rollback-watchdog/v1,
authorized_cold_rollout=true, runtime, snapshot, source_head,
candidate_head, old_agent_sha256, candidate_agent_sha256,
candidate_pid/candidate_token, keeper_pid/keeper_token, port,
deadline_epoch и keeper_task=FF-Bridge-V3-Keeper.

Перед выполнением он сверяет исходную версию и SHA агента с запечатанной
копией. Для успеха нужны три последовательных ответа нового агента
с требуемым SHA и проверенным PID/временем создания. При недоступности
к сроку он может остановить только заранее названный процесс, отдельно
проверив его исполняемый сценарий. Затем он проверяет отсутствие
других экземпляров из заменяемого каталога, восстанавливает SHA-проверенный
снимок и запускает штатный keeper через Task Scheduler. Если чужой
процесс ещё работает, прекращает откат с явным результатом
rollback_blocked, не переписывая чужие файлы.

Важно: это лишь компонент независимого восстановления, а не разрешение
на прерывание текущего Bridge. Его надо проверить с отдельным
контроллером развёртывания и Task Scheduler, прежде чем ставить
боевую задачу. На действующем ПК план не вооружён и сторож не запускался
для завершения пользовательских процессов.
