# Сопровождение репозитория Windows Bridge Core

## Единственный источник правды

Канонический исходный репозиторий — `Ai-b0ss/windows-bridge-core`, ветка `main`. Исторический приватный `windows-agent-bridge` — отдельный архив/транспорт; не зеркалировать его `.git`, секреты и журналы в публичный репозиторий.

Исходники в `main`, последний опубликованный ZIP и установленный Bridge на ПК — **три разные версии**, пока не проверено иное. Слияние PR не обновляет ZIP и не развертывает программу автоматически. Изменять работающий runtime можно только с резервной копией и проверенным откатом.

## Ветки и PR

Одна задача — одна ветка и один PR. Обязательно дождаться проверок CI, затем использовать squash merge. После слияния исходная ветка может быть удалена **только если её текущий HEAD SHA совпадает с SHA, зафиксированным в слитом PR**, а на ветке нет нового открытого PR. Признак `git branch --merged` не годится для squash merge: Git может считать уже слитые изменения отдельной историей.

14 ноября 2026 года найдено 65 веток: `main`, 62 ветки со строго подтверждённым уже слитым PR и две ветки без такого подтверждения. В архиве `tools/maintenance/merged-branches-2026-11-14.json` сохранены имя, SHA и номер PR для каждой кандидатки. Две ветки сознательно сохраняются:

- `feat/trusted-skill-input-20261030`
- `security/pin-public-ci-actions-20261027`

Скрипт `tools/maintenance/prune_merged_branches.mjs` ничего не удаляет без `--apply`. Он повторно получает открытые и закрытые PR и все ветки, сверяет текущий SHA с архивом, факт слияния, происхождение PR из того же репозитория, отсутствие открытого PR и непосредственно перед удалением ещё раз проверяет SHA. Любое несоответствие — сохранение ветки. История слитых PR остаётся в GitHub, а их исходные SHA позволяют восстановить ветку при необходимости.

Workflow `.github/workflows/merged-branch-housekeeping.yml` выполняет read-only проверку при создании PR; после слияния в `main` он **однократно** запускает очистку строго зафиксированного списка. Повторная проверка идемпотентна: отсутствующие ветки пропускаются.

Если workflow не получил право `contents: write` или GitHub запретил удаление конкретной ветки, проверить его отчёт, а не обходить ограничения или удалять вручную без новой сверки. Отчёт выполнения сохраняется в GitHub Actions.

## Восстановление ветки

Для восстановления нужной ветки использовать её `name` и `sha` из JSON-архива и создать `refs/heads/<name>` на указанном SHA через авторизованный GitHub API/CLI. Восстанавливать выборочно, после проверки отсутствия новой ветки с тем же именем. Результаты PR и обсуждения от удаления исходной ветки не исчезают.

## Репозиторий и рабочая Windows

Не останавливать основной Bridge, VPN, процессы других агентов или пользовательский Chrome ради Git-уборки. Изолированные checkout и тесты должны храниться отдельно от установленного runtime. Не включать домашние файлы, профили, локальные абсолютные пути и приватные журналы в публичный GitHub.
