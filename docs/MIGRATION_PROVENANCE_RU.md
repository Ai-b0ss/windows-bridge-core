# Восстановление происхождения установленного Bridge

## Проблема

Установленная версия может содержать файлы из известного нового коммита, но сохранять манифест прежней версии. Запрещено исправлять это простым изменением поля source_head: манифест является заявлением о происхождении, а не доказательством. Штатный установщик правильно возвращает PREVIOUS_MANIFEST_UNPROVEN, если старый source_head не является предком кандидата.

## Проверка без записи

Функция `cua_runtime_deploy.plan_manifest_reconciliation(repo, installed_root, trusted_head=<полный SHA>, ref=<проверенный кандидат>)` возвращает план **только если**:

1. Старый установленный манифест целиком и точно воспроизводится из Git-объектов заявленного коммита: schema, source_head, release_id, files.
2. Независимо выбранный доверенный исходный коммит `trusted_head` задан полным 40-символьным SHA и является предком кандидата.
3. Каждый файл из доверенного Git-дерева существует на диске, имеет разрешённый тип и совпадает по SHA-256 с Git. Проверяются родительские каталоги и запрещены reparse points.
4. Старый набор путей является подмножеством доверенного, а доверенный — подмножеством кандидата; автоматическое удаление через согласование не допускается.
5. Новые имена кандидата не заняты чужими файлами, нет активной транзакции установки, а исходный манифест не изменился за время проверки.

Функция не создаёт, не перемещает, не удаляет и не заменяет файлы, не останавливает процессы и не переводит текущую установку в доверенное состояние. Она возвращает план будущего манифеста, но **не разрешает его запись**.

## Конкретная диагностика 15 ноября 2026 года

На рабочей машине старый manifest v1 ссылается на `cdd9541` (104 записи). Фактически 109 установленных файлов ядра совпадают с Git-объектами `a73aee9`: 92 ранее учтённых файла идентичны обеим версиям, 12 — новой; пять дополнительных тоже доказаны по Git.

В отдельной временной копии подтверждены: отказ установщика со старым manifest, успешное обновление с корректно вычисленным manifest `a73aee9`, восстановление при инъекции сбоя после трёх замен, сохранность пользовательского файла. Рабочая установка и VPN не изменялись.

## Особенности рабочей установки

Путь %LOCALAPPDATA%\FF-Windows-Bridge является Windows junction на
<BRIDGE_ROOT>. Прямая проверка через ссылку правильно возвращает
DEPLOY_REPARSE_OR_TYPE_FORBIDDEN. Для read-only проверки использовать
реальный, заранее проверенный каталог <BRIDGE_ROOT>\bridge-v3.
Это не разрешает автоматическую замену содержимого.

В .cua-deploy остаются четыре старых подкаталога транзакций с
journal.json, backup и stage (сентябрь–октябрь 2026). Активного файла
блокировки не обнаружено. Программа возвращает provenance_verified=true,
но eligible=false, requires_transaction_review=true до разбирательства.
Нельзя удалять журналы или резервные копии на основании одного возраста.

## Следующий выпускной контроль

Только после отдельного решения владельца можно планировать локальную транзакцию: остановка изменяемых компонентов; резервная копия реальных файлов, старого манифеста и пользовательских конфигураций; независимая проверка хешей и возможности отката; доверенное атомарное согласование манифеста; затем обновление и проверка работоспособности. Отказ от любого шага должен оставлять рабочий Bridge в предыдущем состоянии.

Запрещено использовать этот preflight для автоматического `source_head`-relabel, сброса `stop.flag`, обхода проверки происхождения или удалённого «самолечения» без контроля владельца.
