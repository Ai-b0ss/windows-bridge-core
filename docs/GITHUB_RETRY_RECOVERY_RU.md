# Ограниченные повторы GitHub-транспорта

`CommentTransport.process()` выполняет одну попытку и освобождает worker.
Временная ошибка больше не удерживает один из восьми потоков во время backoff.
Диспетчер проверяет сохранённые запросы примерно раз в секунду, включая задания
на старых страницах и в архивных inbox. Время очередной попытки хранится в
`retry_after`; повторное получение того же комментария не отменяет задержку.

## Бюджет и классификация

Параметры задаются только в локальном `github_transport_config.json`:

| Поле | По умолчанию | Допустимый диапазон |
| --- | --- | --- |
| `task_retry_attempts` | 6 попыток, включая первую | 1–32 |
| `task_retry_seconds` | 300 секунд | 1–3600 |
| `task_retry_base_seconds` | 1 секунда | 0,1–30 |
| `task_retry_cap_seconds` | 30 секунд | от base до 300 |

Выходящие за диапазон конечные значения ограничиваются диапазоном. Некорректная
конфигурация останавливает запуск. Поля комментария не управляют этим бюджетом.
Задержка равномерно выбирается в пределах половины и полной величины
`min(cap, base * 2**(attempts-1))`, с ограничением оставшимся временем.

Повторяются известные состояния `REQUEST_NOT_DELIVERED`, `TASK_IN_PROGRESS`,
`INTERACTIVE_SESSION_REQUIRED`; временные сетевые ошибки и занятость SQLite;
HTTP 408/429/500/502/503/504 для операций из существующего списка чтения.
Для подготовки большого результата такие же HTTP-коды считаются временными;
403 повторяется только при действующем GitHub rate-limit cooldown.
Ошибки конфигурации, валидации, доступа, неизвестные исключения помещаются
в карантин; обычные окончательные ответы RPC публикуются как `FAILED`.

Ответ из `journal-cache` окончателен даже при временно выглядящем error_code.
`TASK_OUTCOME_UNKNOWN`, конфликт идентичности и истёкший результат не разрешают
автоматическое повторное выполнение мутации. Существующий transport journal
не изменён.

Бюджет проверяется перед каждой попыткой, счётчик записывается до dispatch.
Работающий процесс использует `time.monotonic()`. При рестарте оставшееся время
уменьшается на прошедшее календарное время; перевод часов назад не увеличивает
сохранённый остаток. Счётчик попыток сохраняет конечный предел и после рестартов.
Дедлайн ограничивает допуск новых попыток: уже начатый RPC не прерывается.
Его существующие сетевые таймауты сохраняются, включая внутренний повтор чтения.
Этот ремонт не меняет GitHub rate-limit pacing подготовки и доставки результатов.

## Сохранение и наблюдение

Исходный GitHub-комментарий остаётся в `pending-requests/<comment_id>.json`.
Новая запись `request-retries/<comment_id>.json` содержит состояние, число
попыток, остаток времени, следующую попытку, причину карантина и идентичность:
репозиторий, comment ID, SHA-256 полного task. При наличии `issue_url` сохраняется
исходный inbox. Редактирование task под тем же comment ID не подменяет запрос:
исходный запрос остаётся на диске и помещается в карантин.

До публикации сохраняется `completed_result`. Ошибка подготовки публикации
или рестарт повторяет этот ответ, сохраняя task/client/comment/node identity.
После создания outbox действует прежняя схема идемпотентной доставки;
повторный PATCH того же комментария не создаёт новый комментарий.
При повторном получении outbox-записи worker не запускается, retry-кеш не растёт,
а исключение при чтении не оставляет comment ID в `active`.

Файлы записываются через flush/fsync и атомарный replace. После записи outbox
новая retry-запись удаляется. Старые pending/outbox-файлы читаются без миграции;
для старого pending-задания бюджет начинается при первой новой попытке.
При повреждении локального файла запрос не исполняется по догадке, остальные
сохранённые запросы продолжают восстанавливаться.

В `comment_transport_health.json` добавлены `scheduled_retries`,
`quarantined_requests`, `quarantine_sample` (не более 16 записей с ID и причиной).
Поле `waiting_for_login` сохранено для ожидания интерактивной сессии.
Карантин виден локальному оператору даже после успешной обработки других задач.
GitHub-комментарий в карантине остаётся исходным запросом; удалённый клиент может
продолжать ожидание до локального восстановления. Секреты и тексты исключений
не записываются в метаданные ошибки retry-записи.

## Локальное восстановление после исправления причины

1. Остановить только соответствующий comment daemon обычным локальным способом.
2. Сделать резервную копию конкретной retry-записи. Сверить репозиторий,
   comment ID и task/client ID с исходным pending-запросом. При конфликте
   редактирования сначала установить, какой исходный запрос разрешён владельцем.
3. В этой записи установить `status` в `waiting`, `attempts` в `0`,
   `remaining_seconds` в локальный `task_retry_seconds`, `saved_at` в текущее
   время Unix в секундах, `next_retry_at` в `0`. Удалить поля `error_code`,
   `quarantine_reason`, `retryable`. Сохранить атомарно. Сохранить остальные поля,
   особенно `identity`, `inbox_issue`, `received_at_ms` и `completed_result`.
4. Запустить daemon. Он восстановит тот же запрос/ответ без нового task ID.

Не удалять journal, исходный pending, outbox или `completed_result` ради повтора.
Локальный сброс бюджета не отменяет `TASK_OUTCOME_UNKNOWN` и не разрешает
повтор мутации с неизвестным исходом. Для этого требуется отдельное выяснение
результата; создание нового task ID может обойти дедупликацию и здесь не предлагается.
При откате на старый daemon новые файлы не мешают старым форматам, но старое
поведение бесконечных повторов вернётся, а карантин перестанет соблюдаться.

## Проверки без внешних сервисов

`python -m unittest discover -s tests -p test_github_bounded_retry.py` проверяет
реальный пул из восьми потоков, 200 здоровых заданий рядом с отравленным,
исчерпание бюджета и рестарт, jitter, монотонный дедлайн, классификацию,
точную идентичность, outbox, потерю ACK и journal-дедупликацию.

`python tests/integration/github_retry_crash_smoke.py` аварийно завершает два
отдельных процесса после единственного синтетического эффекта: до записи ответа
и после фиксации результата в journal. Новый процесс не повторяет эффект.
Все эффекты, состояния и маркеры этих проверок находятся во временных каталогах;
соединение с GitHub и установленным Bridge не требуется.
